# Skills

The capitalized words REQUIRED, MUST, MUST NOT, RECOMMENDED, SHOULD,
SHOULD NOT, OPTIONAL, and MAY are to be interpreted as described in
[IETF RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

## Project overview

This is a curated collection of agent skills for AI-assisted and agentic
software development. The skills encode established development practices —
SDLC phases, version control conventions — into reliable prompts. These
prompts are designed to produce consistent, predictable outputs across
mainstream coding models.

Each skill is portable and independent. No skill hands off to another skill.
You can install or delete any one skill on its own, and orchestrate them
into all sorts of workflows.

Every `SKILL.md` file SHOULD be token-efficient (RECOMMENDED limit: 500
lines, counting blank lines) and MUST pass the validator checks — described
below.

## Tech stack

- Bash (installer and validator scripts).

- `pre-commit` (Python) for Git hooks.

- `skills-ref` (Python, OPTIONAL) for canonical `SKILL.md` validation.

- GitHub Actions for CI.

## Project structure

- **`skills/`**
  One subdirectory per skill, each containing a `SKILL.md` (for agents)
  and a `README.md` (for humans).

- **`skills/create-skill/`**
  Use this to author new skills, both in this repository and in downstream
  projects. It bundles the canonical template (`assets/create-skill-template/`),
  the validator (`scripts/`), and reference docs (`references/`).

- **`build/`**
  Compiled agent-specific artifacts generated by `./run/install`. Do not
  edit directly.

- **`run/`**
  Dev tools. Just the `install` script, for now.

- **`docs/`**
  Documentation for human maintainers and contributors.

- **`skills.sh.json`**
  Controls how skills in this collection are presented on the
  [skills.sh](https://www.skills.sh/) website.

- **`CHANGELOG.md`** Version history.

- **`CONTRIBUTING.md`** For humans only.

## Tools

- **`./run/install --help`** to build and install skills into supported agents.

- **`./skills/create-skill/scripts/create-skill-validate.sh <skill_dir>`** to validate
  a skill directory before committing.

- **`pre-commit run --all-files`** for linting commit messages
  (requires `pipx install pre-commit && pre-commit install`).

## Rules

- MUST follow the **[branch](./skills/branch/SKILL.md)** skill for all
  branch names.

- MUST follow the **[commit](./skills/commit/SKILL.md)** skill for all
  commit messages.

- MUST run the validator on any new or modified skill before committing.

- To add or improve a skill, MUST use the
  **[create-skill](./skills/create-skill/SKILL.md)** skill. See also
  [`docs/creating-skills.md`](./docs/creating-skills.md).

- Skill-authoring conventions — required file structure, `SKILL.md` section
  order, the line budget, discoverable artifact stores, no cross-skill
  references, and so on — are defined by the
  **[create-skill](./skills/create-skill/SKILL.md)** skill, not restated
  here. Where this document and `create-skill` ever disagree, `create-skill`
  governs: it is what the validator checks and what an authoring agent
  actually loads.

- A skill that changes the working tree MUST either commit that change as
  its own last step, or explicitly leave it uncommitted for another actor
  to file — never one by default and the other by omission.

  Commit when the edit is itself a complete, commit-worthy unit of work:
  implementing a plan step, fixing a bug, performing a refactor move,
  normalizing style. Each of these has its own type in the
  **[commit](./skills/commit/SKILL.md)** skill's vocabulary (`step`, `fix`,
  `refactor`, `style`, and so on), which is what marks it as a change the
  skill itself is responsible for closing out.

  Leave the change uncommitted when the skill only polishes or verifies
  content that another change already produced or will produce —
  proofreading prose, auditing, reviewing, testing, validating. That skill's
  edits, if it makes any, stay in the working tree for the change's
  originator, or the user, to fold in and file.

  A skill that commits MUST stop at that commit. Pushing, opening a review,
  merging, and releasing are out of scope for a single skill.

  **[commit](./skills/commit/SKILL.md)** itself is neither case: it composes
  the message, and the changelog entry where one is due, that another actor
  will use to file the change. It MUST NOT stage or commit anything itself.

  A skill MUST NOT decide branch policy. It commits, or proposes to commit,
  on whatever branch is already checked out. Whether that branch is a
  protected trunk is for the repository's own conventions and the
  **[branch](./skills/branch/SKILL.md)** skill to have already settled, not
  something a change-making skill gates on.

- MUST NOT commit anything under `build/`. It is gitignored. Only
  `build/README.md` is tracked.
